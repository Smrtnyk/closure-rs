## Resolution

- status: fixed in #3 (`TypeCheck#checkTypeofString` quotes the string as Java's UTF-8 error stream
  writes it; diagnostic arguments taken from Java strings use the Display text).
- root cause: diagnostic messages are Rust `String`s. Arguments taken from a Java string (a string
  literal, a namespace) were converted with `JsString::to_string_lossy`, which turns an unpaired
  surrogate into U+FFFD. Java keeps the surrogate in the message and its UTF-8 error stream
  (PrintStream, and the OutputStreamWriter of `--error_format=JSON`) writes the encoder's
  replacement `?`. The crate already has that conversion (`charset::utf8_encoded_text`, used by
  `JsString`'s `Display`).
- fix: `TypeCheck#checkTypeofString` and every report site that passed `x.to_string_lossy()` as a
  diagnostic argument (`&[&x.to_string_lossy()..]`, 53 lines, plus
  `GatherModuleMetadata`'s namespace argument) use `x.to_string()` (Display). The comparisons in
  checkTypeofString are unaffected (the valid names are ASCII).
- the same bug at another site: `goog.provide('a\uD800')` / `goog.module('\uDC00b')`
  (JSC_INVALID_NAMESPACE_OR_MODULE_ID printed `a�` instead of `a?`).
- regression tests: `crates/cli/tests/data/fuzz_regressions/typeof-lone-surrogate/`,
  `typeof-lone-surrogate-json/` and `namespace-lone-surrogate/`.
- same root cause: a further finding of seed 2001 under the sourcemap profile (same warning).
- known limit: a diagnostic argument computed into a variable before the report call (not inline in
  the argument array) may still use the lossy conversion.
