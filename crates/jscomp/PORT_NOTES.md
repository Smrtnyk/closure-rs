# closure-jscomp port notes

These notes record where the Rust shape of `closure-jscomp` differs from the Java it ports, and
why. The general conventions (arena, handles, borrowing, strings, collections) are in
[crates/DESIGN.md](../DESIGN.md); this file covers the class-specific cases. Java tests that are
`@Ignore`d in Java (JUnit never runs them) are not ported. Tests of `CompilerTestCase`,
`IntegrationTestCase` and `CompilerTypeTestCase` subclasses run as unit-corpus records
(`crates/testing`). A few Java tests cannot be expressed in Rust: for example
`VariableMapTest#testReverseLookupOfNullFindsNoName` passes `null` where the Rust API takes a
`&JsString`, and `NodeTraversalTest#testNodeTraversalInterruptable` needs a JVM thread interrupt
(see `Platform` below). The only deliberately unported
pass factories in `DefaultPassConfig` are the out-of-scope ones (PolymerPass, ChromePass,
ReplaceMessagesForChrome, CoverageInstrumentationPass; each marked `// unported:`).

## Diagnostics and error reporting

- `DiagnosticType` constants keep static string fields and key-based equality; constants with
  computed class-init text use `LazyLock<DiagnosticType>` and `String::leak`. Java identity
  comparisons use pointer equality.
- `JSError` keeps `NodeId` identity. Formatter and report methods receive the `Ast`, and FULL
  formatting reads live node lengths. `SourceFile` keeps WTF-16 code and computes offsets and
  counts in UTF-16 units.
- Excerpt lines become Rust `String`s through
  `closure_rhino::java_lang::charset::utf8_encoded_text`, which writes each unpaired surrogate as
  `'?'` as Java's UTF-8 `PrintStream` does (one UTF-16 unit, so caret columns are unchanged).
  Code that passes `JsString` text (identifiers, literal values) as `JSError` arguments converts
  it with the same function, never with a lossy U+FFFD conversion
  (`tests/surrogate_excerpt_test.rs`, generated by `tests/java/SurrogateExcerpt.java`).
- `BasicErrorManager` is an abstract-base trait; concrete managers own its `SortingErrorManager`
  storage. `ComposeWarningsGuard` keeps its sorted guards behind a mutex and snapshots them when
  flattening, including Java's self-add case. The thread-safe delegating manager exposes
  synchronized shared-receiver entry points as well as the `ErrorManager` trait.
- `SourceFile` lazy state uses mutexes and double-checked loading. The zip cache uses
  last-modified timestamps and LRU eviction; Java's cache-size system property is the environment
  variable `jscomp.zipfile.cachesize` (default 1000). Zip entries are read eagerly into owned
  byte vectors.
- Object.toString identity hashes of unnamed groups/guards use data addresses; these never reach
  compiler output.
- `Platform` has no JVM interrupt flag or managed heap: the interruption hook returns false and
  the free/total-memory hooks return zero. `JvmMetrics` has no JVM management beans either. These
  are native runtime boundaries, not claims of JVM equivalence.
- The JSTypeRegistry's error reporter: Java's `RhinoErrorReporter.forOldRhino(compiler)` calls
  back into `Compiler#report`. The Rust Compiler owns the registry, so its
  `QueueingOldRhinoErrorReporter` queues the `JSError` and the Compiler reports the queue before
  it next reports or reads errors. Error managers sort errors, so output is unchanged; only an
  options `ErrorHandler` sees registry errors later. The registry shares the Compiler's
  forward-declared-types set, as Java's constructor keeps the `Set`.
- Java's Compiler is the ModuleLoader's `ErrorHandler`. The Rust loader keeps a shared
  `Arc<Mutex<dyn ErrorHandler>>` and queues reports for the compiler; `ModuleMapCreator` calls
  `Compiler::flush_module_errors` right after each `resolveJsModule`, where Java reports, so
  `JSC_JS_MODULE_LOAD_WARNING` keeps its order relative to the map's own diagnostics.

## Compiler, inputs and chunks

- `Compiler` owns the `Ast` and the scope arenas and derefs to `Ast`; `AbstractCompiler` is an
  alias of `Compiler`. Split-borrow accessors such as `get_type_registry_and_ast` and
  `get_coding_convention_type_registry_and_ast` are Rust-only: they hand out the parts Java reads
  through implicit `this` at the same time.
- `JSChunk` and `CompilerInput` keep shared object identity; an input holds a weak reference back
  to its chunk. `CompilerInput#getPath` never returns null in this port, so Java's
  `modulePath == null` early returns are omitted where they occur. `LinkedHashMap`/`LinkedHashSet`
  order is `IndexMap`/`IndexSet`. `JSChunkGraph` uses packed bitsets and Java UTF-16 name order.
- `ChangeTracker`'s stamp is an `Arc<AtomicI32>`, so `ScopedChangeHandler` can read it without
  keeping a compiler borrow; stamp values and notification timing are Java's. Listener identity
  uses `Arc::ptr_eq`; `RecentChange` is shared through `Arc<Mutex<_>>`. `Timeline` event identity
  uses never-shrinking `Vec` indices.
- `CompilerOptions` callbacks that Java mutates (`CompilerPass`, `ErrorHandler`,
  `ErrorReportGenerator`) are `Arc<Mutex<...>>`; the options' shallow `Clone` keeps their identity.
  `CodePrinter.Builder` borrows the caller's options, as Java's assignment does, and owns a
  default instance when none is set.
- `DefaultPassConfig` keeps every factory field and `TranspilationPasses` factory in Java order,
  with loop flags, conditions, preconditions and ordering assertions. `PassListBuilder` keeps the
  full metadata (`build_including_unported`); execution skips factories registered as unported.
  The anonymous `CompilerPass` of `checkRegExp`/`checkRegExpForOptimizations` is the named
  `CheckRegExpAndRecordGlobalReferences`. `combineChecks` returns a `CombinedChecks` that owns
  the boxed callbacks and lends them to a `CombinedCompilerPass` per `process`.
- `CompilerExecutor` runs the compile on a scoped thread with Java's 64 MiB stack and thread
  name. A scoped Rust thread must finish before the borrowed compiler is returned, so a timeout
  is detected at the deadline and raises `java.util.concurrent.TimeoutException`, but unwinding
  waits for the worker; Java shuts the executor down without waiting. Only elapsed time differs.
- `ChangeVerifier` has its own read-only pre-order walk: `NodeUtil::visit_pre_order` takes
  `&mut Ast`, while verification holds an immutable compiler. The order is Java's and nothing is
  mutated.
- The `Tracer` report and the `PerformanceTracker` code-size estimates are byte-identical to Java
  (`tests/tracer_test.rs`, `performance_tracker_test.rs`). The gzip estimator needs the native
  zlib backend: zlib-rs differed by one compressed byte, so the workspace `flate2` and `zip`
  use native zlib.

## NodeUtil, traversal and scopes

- LHS visitor methods use one generic body over the Rust-only `AstContext` (`ast()`/`ast_mut()`,
  implemented for `Ast` and `Compiler`); consumers receive the caller's mutable context and run
  during the walk, including ScopeScanner redeclaration handlers.
- `NodeUtil.NUMBER_NAN` is a static `QualifiedName` matcher for `"Number.NaN"`, because a Java
  static `Node` has no arena to live in; the matching is the same.
- `NodeUtil#getParentChangeScopeNodes` returns `Vec<Option<NodeId>>` to keep a possible Java null
  member.
- `NodeUtil#getOriginalName` keeps Java's default regex `$` anchor before a final LF, CR, CRLF,
  NEL, U+2028 or U+2029; Java's default `\d` is ASCII.
- `ScopedName` is ported because `AbstractVar` inherits its equality (name plus scope-root
  identity). `VarId` handles keep identity `Eq`; code that needs Java's `Set<Var>.contains` (for
  example the escaped-locals sets of LiveVariablesAnalysis and DeadAssignmentsElimination, built
  from recreated scopes) calls `VarId::equals` explicitly.
- Lazy implicit-variable lookups take a mutable compiler because they can allocate; metadata
  readers take an immutable compiler.
- rhino's `StaticScope`/`StaticSlot`/`StaticRef` traits return references, so they cannot return
  Compiler-owned `ScopeId`s: `Scope`/`Var` do not implement them directly. The same methods exist
  on the handles, a test-only arena-handle adapter covers
  `StaticScope#getTopmostScopeOfEventualDeclaration`, and code that needs a `StaticScope` (for
  example `JSTypeRegistry#getType`) uses the leaked views below
  (`crate::scope::as_static_scope(compiler, ScopeId)`).
- NodeTraversal and ScopeCreator carry `AbstractScopeHandle {Untyped(ScopeId), Typed(TypedScope)}`
  (Java's `AbstractScope<?, ?>`), so `getTypedScope` returns the typed scope from the stack. The
  cached CFG of a traversal is boxed.

## TypedScope and TypedVar views

- **Storage.** `TypedScope`/`TypedVar` are `Copy` handles into
  `Compiler.typed_scope_arena: Arc<RwLock<TypedScopeArena>>`; the syntactic `ScopeArena` is shared
  the same way (`Arc<RwLock<ScopeArena>>`). nodeutil's `AbstractScope`/`AbstractVar` traits read
  entries through GAT guards (`DataRef`/`DataMut`): plain references for `ScopeId`/`VarId`,
  `TypedArenaRef`/`TypedArenaMut` lock guards for the typed arena.
- **Leaked canonical views.** closure-jstype's `StaticTypedScope`/`StaticTypedSlot` traits return
  `&dyn` references, and NamedType compares scopes by address (Java `!=`), while the data they
  view lives in the compiler's arenas and changes. So each TypedScope, TypedVar, Scope and Var the
  registry touches gets exactly one view, created on first use, cached in its arena entry
  (`OnceLock<&'static ...>`) and never freed (`Box::leak`); it holds only a `Weak` to the arena.
  The cost is a small allocation per scope (about 40 bytes) and per var (about 16 bytes) that the
  registry touches. Accessors: `TypedScope::as_static_typed_scope(_arc)`,
  `TypedScope::from_static_typed_scope`, `TypedVar::as_static_typed_slot`,
  `crate::scope::as_static_scope(compiler, ScopeId)`. View methods are read-only twins of the
  compiler-side methods (implicit vars are visible only once materialised).
- `StaticTypedScope::get_type_of_this(&self, reg: &JSTypeRegistry, ast: &Ast)` computes the type
  at call time from the root's JSType and the registry, as Java does.
- `AbstractVar::to_string(&AbstractCompiler)` (used only in precondition panic messages) prints
  the TypeId debug form for typed vars, because `JSType#toString` needs `&mut JSTypeRegistry`;
  `TypedVar::to_string(&mut compiler)` is the faithful one.
- `JavaHashCode` for `TypedScope` (LinkedFlowScope's HamtPMap keys) is the arena index. Java's
  identity hash is JVM-dependent, so no output may depend on it.
- `ModuleRenaming#getNameRootType`'s nullable `TypedScope globalTypedScope` is
  `GlobalTypedScope::{None(&Ast), Some(&mut AbstractCompiler, TypedScope)}`, because a
  TypedScope's vars live in the compiler, which also owns the AST the GOOG_MODULE branch reads.
- `ModuleImportResolver`'s fields `nodeToScopeMapper` and `registry` are passed per call
  (`NodeToScopeMapper = &dyn Fn(Option<NodeId>) -> Option<TypedScope>`) and through the compiler.
- `TypeValidator`: the compiler holds an `Arc<TypeValidator>`; `getTypeValidator` hands out a
  clone (Java's passes keep the validator in a field while using the compiler) and every method
  takes the compiler. Its two mutable fields (`subtypingMode`, `mismatches`) are behind mutexes
  never held across a compiler call. Java's `instanceof UnknownType` in `expectSuperType` is an
  identity test against UNKNOWN_TYPE/CHECKED_UNKNOWN_TYPE, the only two UnknownType objects.
  `WellFormedTemplatizedTypeVerifier` records its single report and the caller makes it after the
  visit (the report is always the visit's last action). Java overloads are split into
  `expect_can_assign_to_property_of` / `expect_can_assign_to_property_of_type`,
  `register_mismatch_and_report_diagnostic` / `register_mismatch_and_report`,
  `mismatch_native` / `mismatch`.

## Control flow and data flow

- The CFG composes `LinkedDirectedGraph<Option<N>, Branch>`; `None` is Java null and formats as
  `null`. Java's private `AstControlFlowGraph` subclass is a flag that selects its AST priority
  comparator.
- AST values are formatted lazily, at print time, with the live compiler
  (`format_node_value(compiler, value)`, the `with_compiler(compiler)` Display/Graphviz view), so
  AST mutations show up exactly as Java's `Node#toString` would. CFA creates edges without
  formatting or caching node text.
- `ast_position` is a `LinkedIdentityHashMap<Option<NodeId>, i32>` with Java's null-key mapping.
  `UniqueQueue` uses sorted insertion when a comparator exists, FIFO otherwise; its polling order
  is Java's.
- `finally_map` is `IndexMap<NodeId, IndexSet<Option<NodeId>>>`. Java's Guava `HashMultimap` is
  identity-hashed and its value order varies between JVM runs; insertion order here only affects
  the order of ON_EX out-edges when one key has two or more values. Edge membership, priorities,
  joins and sorted DOT output are identical.
- `NodeId` and `VarId` implement `JavaHashCode` with their arena index. Java's identity hashes,
  and so HAMT iteration order, vary between JVM runs; analyses select `JavaHashCode` explicitly
  where identity is meant.
- `DataFlowAnalysis` is a trait plus an owning state struct; `get_cfg_mut`/`into_cfg` hand the
  CFG on to sequential analyses. `Definition` values are `Arc`-shared (equality still compares the
  node). Lattice clones exist only for ownership; `stepCount` is compared before the increment and
  each branched edge gets its annotation right after `branchFlow`, as in Java.
- Compiler access for TypeInference: its entry lattice, joins and `LinkedFlowScope#equals` need
  the compiler, so `create_entry_lattice`, `join_inputs`, `get_input_from_edge`, `join` and
  `FlowJoiner::join_flow` take `&mut AbstractCompiler`, and the lattice bound is the Rust-only
  `LatticeEquals` (`lattice_equals(&self, compiler, other)` is Java's `equals` as `#flow` calls
  it). `FlowBrancher<L, A>` also receives the analysis that created it, because Java's branchers
  are inner classes; closures remain branchers. `FlowScopeJoinOp` exposes inherent
  `join_flow`/`finish` for type inference.
- `NodeTraversal.AbstractCfgCallback` subclasses (DeadAssignmentsElimination,
  CoalesceVariableNames, CheckUnreachableCode, CheckMissingReturn) keep the superclass's cfg-root
  stack with Java's enter/exit order. `AbstractCfgCallback::get_control_flow_graph_mut` is
  Rust-only (the Java callbacks annotate the graph they get). `GraphReachability`'s edge predicate
  carries a lifetime so it can read the AST.
- `java.util.BitSet` (`closure_rhino::java_util::bit_set`): clone trims a non-sticky source's
  capacity in Java; an atomic capacity keeps that effect through `Clone`'s shared receiver.
- DotFormatter truncates labels in UTF-16 units (`MAX_LABEL_NAME_LENGTH` = 10) and encodes with
  the JDK UTF-8 encoder's replacement for lone surrogates, including a pair split at the tenth
  unit. `DotFormatter#key` calls `JSType#to_string` with the compiler's registry, so its entry
  points take `&mut AbstractCompiler`.

## Java HashMap and HashMultimap order

Where Java iterates a `HashMap`/`HashSet` keyed by strings, the order is observable and is
simulated: `closure_rhino::java_lang::hash_map::iteration_order` (checked against the JDK in
`crates/rhino/tests/java_hash_map_test.rs`) and `JavaHashMultimap` in `remove_unused_code.rs`
(table 16, `putVal`, `removeNode`, resize split). Tree bins (9+ keys in one bucket of a 64+
table) panic rather than guess. Sites: PureFunctionIdentifier's `referencesByName` (order of
`JSC_UNUSED_ARTIFICIAL_PURE_ANNOTATION` reports), RemoveUnusedCode's
`removablesForPropertyNames` and `polyfills`. Collections keyed by object identity hashes, which
Java does not fix, keep insertion order: the value sets of those multimaps,
RewriteGlobalDeclarationsForTryCatchWrapping's `ArrayListMultimap<JSChunk, Node>` (observable only
when every chunk shares one insertion root), and CheckConformance's `HashMultimap<Precondition,
Rule>`, whose categories use the fixed order seen in the oracle corpus
(`Precondition::canonical_rank`) with rules in insertion order inside a category.

## Pass notes

### modules

- `UnresolvedModule` objects (reference equality, mutable caches, mutually recursive
  resolution) live in the arena `modules::unresolved_module::UnresolvedModules`, owned by
  `ModuleMapCreator`; `UnresolvedModuleId` is the reference. The abstract class is an enum over
  its four Java subclasses, and the abstract methods dispatch on the handle. Immutable fields sit
  behind an `Arc` so a method can read them while resolving other modules through the arena.
- `ModuleRequestResolver#resolve(Import|Export)` take the compiler (they read line information
  from nodes).
- `ResolveExportResult` is a shared handle: `EsModuleProcessor` compares results by reference, so
  `ptr_eq` is Java's `==`, and `AMBIGUOUS`, `NOT_FOUND` and `ERROR` are process-wide singletons.
- ProcessCommonJSModules keeps no compiler; instance methods that read it are associated functions
  taking it. The static overloads keep the plain names (`is_common_js_import`, ...); the instance
  overloads that read the resolution mode are `*_with_options`. FindImportsAndExports, the
  loader's `ErrorHandler` in Java, hands the loader a `FinderErrorHandler` that pushes into its
  shared error list. `ExportInfo` (identity in Java) compares all fields: each one wraps a
  distinct node. Visitors that only read the tree collect nodes in pre-order first and report
  afterwards, because the arena is borrowed during the walk.
- ConvertChunksToESModules: Java catches the `IllegalArgumentException` of
  `ModuleLoader.relativePathFrom`; Rust has `ModuleLoader::try_relative_path_from` and
  `UnixPath::try_relativize` returning `Result<_, String>` (the exception message), and the
  panicking functions are thin wrappers.

### checks

- CheckSuper keeps its `Context` objects in an index arena (Java compares them by identity).
- CheckTypeImportCodeReferences matches `goog.requireType` with a `QualifiedName`.
- CheckAccessControls: `ImmutableMap<StaticSourceFile, Visibility>` is `FileVisibilityMap`, keyed
  by the address of the shared `Arc<dyn StaticSourceFile>` (neither source-file class overrides
  `equals`); `HashBasedTable<JSType, String, ConstantDeclaration>` is `ConstPropertyTable`,
  bucketed by `JSType#hashCode` and only read with `get`/`putIfAbsent`, never iterated. The
  null-permissive `Deque<ObjectType>` is a `Vec<Option<TypeId>>` whose end is the front.
  `PropertyReference` keeps its AutoBuilder shape; its lazy `readableTypeName` supplier is the
  closed enum `ReadableTypeName` of the three lambdas Java passes. A null source file in the
  package checks panics with `expect("NullPointerException")`, as Java dereferences it.
- ImplicitNullabilityCheck's read-only visitor lists the nodes in pre-order first, then runs its
  body on each (it needs the registry and the traversal's scope).
- CheckConformance: the conformance.proto messages (`conformance_config.rs`) are proto2 with
  `Option` has-bits and a reflection surface that drives the TextFormat parser and printer
  (`protobuf/text_format.rs`) and the binary wire format, written in field-number order. Parsing
  skips undeclared fields and enum numbers (Java keeps them as unknown fields). CUSTOM rules load
  a `java_class` by reflection in Java; the port cannot and reports them unported.

### messages

- `XtbMessageBundle` parses with `closure_rhino::java_lang::sax_parser`, a port of what the JDK 21
  Xerces SAX parser does in the configuration `createSAXParser` sets up (not validating, not
  namespace aware, no external entities or DTD): the ContentHandler calls, the splitting of
  character data into `characters()` calls, skipped undeclared entities, internal entities and
  `<!ATTLIST` defaults, the `XMLMessages.properties` fatal-error texts with line/column, and the
  `[Fatal Error]` line on stderr. `XMLChar`'s table is `crates/rhino/src/java_lang/xml_char.rs`.
  Parity with the JDK is checked by `tests/xtb_message_bundle_java_parity_test.rs`.
- Known differences: each entity is scanned as one buffer, while Xerces refills an 8K buffer, so
  a run of character data crossing a refill boundary splits into `characters()` calls
  differently. Only the number of string parts of a message can differ; ReplaceMessages merges
  consecutive parts, so output is unaffected. The column of a malformed UTF-8 byte is
  approximated. Encodings: UTF-8 (with or without BOM), UTF-16 with a BOM, US-ASCII and
  ISO-8859-1; an XML declaration naming another encoding is reported as `Invalid encoding name`.
  A malformed bundle returns `Err`, and the CLI reports the `java.lang.RuntimeException` with
  Java's message (without the Xerces stack frames).
- Every `ReplaceMessages#get*Pass()` consumes its `ReplaceMessages` (Java's inner pass classes
  share an outer instance that holds only final fields).

### optimizations

- PureFunctionIdentifier: summaries live in an arena referred to by `SummaryId`; the reverse call
  graph is `LinkedDirectedGraph<SummaryId, SideEffectPropagation>`. Java's static detached
  `IMPLICIT_PURE_FN` becomes a detached `function(){}` per instance in the compiler's arena (only
  its identity is used). `OptimizeCalls.Builder#setCompiler` only records that it was called; the
  compiler is passed to `process`. `ReferenceMap#getFunctionNodes` is an `IndexMap` (Guava
  `ImmutableListMultimap` order).
- InlineFunctions: `FindCandidateFunctions` holds `&mut InlineFunctions`; `CallVisitor<C>` owns
  its callback, so the function map and the injector are borrowed apart. The `Function` interface
  is an enum. `resolveInlineConflicts` visits states by index. FunctionArgumentInjector's static
  `THIS_MARKER_NODE` is `this_marker_node(ast)`, created in the arena it is paired with.
  FunctionInjector's sentinel nodes are variants of the private `InnerFunction` enum; its
  throwaway name supplier is a closure over an `AtomicI32`. RenameLabels wraps its
  `DefaultNameGenerator` in a `Mutex` so the supplier is `Send + Sync`.
- CoalesceVariableNames shares its `MemoizedScopeCreator` with its traversal through
  `Rc<RefCell<..>>`; the coloring tie breaker is precomputed per var.
  DeadPropertyAssignmentElimination keeps `Property` objects in a `Vec` arena with an
  `IndexMap` name index.
- RemoveUnusedCode: `Removable`, `VarInfo` and `PolyfillInfo` are arenas owned by the pass
  (`RemovableId`, `VarInfoId`, `PolyfillInfoId`); each Java subclass is an enum variant.
- DisambiguateProperties/AmbiguateProperties: `DisambiguateArena` owns every `ColorGraphNode` and
  `PropertyClustering`; `ColorGraphNodeId`/`PropertyClusteringId` stand for object identity, and
  methods take the handle first and the arena second. ColorGraphBuilder and
  ColorFindPropertyReferences receive the node factory and the arena as arguments. UseSiteRenamer's
  mutation callback receives the AST owner it mutates. AmbiguateProperties' property-graph nodes
  carry a `PropertyKey`. The factory's overridable methods are the trait
  `ColorGraphNodeFactoryMethods` (a replay stub overrides `createNode`).

## Replay-only accessors

Some classes have Rust-only read accessors of private fields (`replay_fields`, for example on
`CheckRegExp`, `ColorGraphNodeFactory`, `ColorRegistry`; `StringPool.Builder#max_length`) and
constructors made public, for the unit-record replay in `crates/testing`, which dumps object state
the way Java reflection (`Field#get`) does. They have no Java counterpart and no effect on
compilation.

## JVM-generated test fixtures

Tests read committed fixtures and need no JVM; the Java helpers that produced them are in
`tests/java/`.

- `tests/data/d2_stderr_fixture.jsonl`: D2 diagnostic output (warnings, multi-line excerpts, tabs,
  non-ASCII text, negative locations, original mappings), selected by `tests/make_d2_fixture.py`
  from a capture of the reference jar's stderr; rows whose stderr contains Java stack traces
  printed outside the report generator are excluded and listed in
  [tests/data/D2_EXCLUSIONS.md](tests/data/D2_EXCLUSIONS.md). The full capture can be replayed
  with the `d2_stderr_check` example.
- `tests/data/compiler_diagnostic_groups.json`: every DiagnosticGroups registration and public
  field with members, levels and formats ([tests/java/COMPILER_DIAGNOSTIC_GROUPS.md](tests/java/COMPILER_DIAGNOSTIC_GROUPS.md)).
- `tests/data/compiler_whitespace.json`: Compiler WHITESPACE_ONLY output and diagnostics on 32 D2
  cases ([tests/java/COMPILER_WHITESPACE.md](tests/java/COMPILER_WHITESPACE.md)); the full run
  uses the `compiler_whitespace_check` example.
- `tests/data/compiler_pass_lists.json`: the pass lists DefaultPassConfig builds for 14 option
  configurations (`default_pass_config_test.rs`, `tests/java/CompilerPassLists.java`).
- `tests/data/names.tsv`, `names.sha256`, `variables.expected.tsv.gz`: DefaultNameGenerator
  configurations with Java digests and VariableMap expectations (`namegen_golden_test.rs`); the

- `tests/data/message_format_cases.json`, `source_file_io_cases.json`, `zip_input_cases.json`,
  `compiler_estimator.json`, `compiler_tracer_report.txt`: MessageFormat, charset decoding, zip
